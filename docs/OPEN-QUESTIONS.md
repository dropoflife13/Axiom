# Open Questions & Architectural Decisions

This document tracks unresolved design questions, trade-offs, and open exploration areas for the Axiom engine.

---

## 1. Initial Domains in Scope

- Which domains in `brain/02-domains/` should serve as the initial cohort for candidate generation and verification?
- Candidates for initial focus:
  - Technical / Mechanizable: `authorization.md`, `cybersec.md`, `ui-frontend.md`, `data-science.md`.
  - Architectural / Operational: `solutions.md`, `business-analysis.md`.
- Criteria for selection: Domains with clear executable invariants and high frequency of testable anti-patterns.

---

## 2. Check-Spec Format for Level 3 (L3) Verification

- What specification format should express L3 executable checks?
- Options under consideration:
  - **Regex / AST pattern matching:** Lightweight, fast, deterministic; limited semantic awareness.
  - **Semgrep rules:** Declarative code pattern matching across multiple programming languages.
  - **SQL Linters (e.g., SQLFluff):** Specialized for database and query schema rules.
  - **Custom TS/JS evaluators:** Full programmatic expressiveness with sandboxed execution.
- Goal: Define a clean, serializable check-spec schema that can validate both compliant and violating fixture files.

---

## 3. Seed Fixture Authoring & Ownership

- Who writes the initial positive (compliant) and negative (violating) seed fixtures?
- Human engineers/domain experts must write the baseline ground-truth fixtures.
- Criteria for fixture completeness: Every testable rule must have at least one clean passing fixture and at least one failing fixture triggering the exact boundary condition.

---

## 4. Primary Free LLM API Selection

- Which free OpenAI-compatible API endpoint will serve as the default provider for the Executor?
- Candidates:
  - Google Gemini API (via OpenAI-compatible endpoint or free tier).
  - Groq / Together AI free tiers.
  - Ollama / vLLM local endpoints for zero-cloud testing.
- Requirement: Must support standard OpenAI SDK chat completion interfaces (`baseURL` + `apiKey`).

---

## 5. Preventing Fixture Circularity

- **Circularity Risk:** If the Executor generates both the rule and the fixture, it can create tautological tests that pass by definition while failing real-world validity.
- **Strict Invariant:** Fixtures must **never** be generated by the Executor.
- All verification fixtures must be authored by humans or generated from verified external golden sources (e.g., historical PR diffs, static analysis suites, known vulnerability datasets) prior to candidate generation.
